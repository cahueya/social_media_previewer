# Social Media Previewer for Concrete CMS 9+

This package adds a **Social Media Preview** button to the Concrete toolbar using the official `addPageHeaderMenuItem()` interface. The button opens an accessible modal containing local previews for X, Telegram, Facebook, Nostr, LinkedIn, Bluesky, and Mastodon, together with checks for missing or unsuitable metadata.

Platforms can be selected in several ways: directly through the tabs, with the previous and next buttons, using the `←` and `→` arrow keys (`Home` and `End` are also supported), or by swiping horizontally across the preview on touch devices.

## Data sources and priority

The currently displayed page is analyzed again whenever the modal is opened. This ensures that the preview also reflects changes made since the page was initially loaded.

Data sources are evaluated in the following order:

1. Platform-specific metadata (`twitter:*` for X)
2. Open Graph metadata (`og:*`)
3. Standard HTML metadata (`title`, meta description, and canonical URL)
4. Concrete page attributes (`meta_title`, `meta_description`, `thumbnail`, page name, and description)
5. JSON-LD and the first suitable H1, paragraph, and content image

The modal displays the actual source used for each field.

No platform APIs or crawlers are contacted. Preview images referenced by the page metadata are loaded directly by the browser. If the image uses an external URL, the browser will make a regular image request to that host.

## Installation

1. Copy this directory to `packages/social_media_previewer` in your Concrete installation.
2. Open **Extend Concrete → Add Functionality** in the dashboard and install the package.
3. Open a frontend page while signed in with access to the Concrete toolbar.

The preview is available only on frontend pages. The toolbar item and its assets are not loaded on `/dashboard` or any path below `/dashboard/`.

The package requires Concrete CMS 9.0 or newer.

The namespace follows the Concrete convention derived from the package handle:

```php
Concrete\Package\SocialMediaPreviewer
```

The interface uses the Bootstrap UI provided by Concrete CMS and scoped through `.ccm-ui`. The modal, tabs, status colors, alerts, grid, spacing, and responsive utilities are not reimplemented by the package.

The custom stylesheet only contains the platform-specific card designs and the few additional rules required for swipe handling and preview dimensions.

All user-interface source strings are written in English. Complete German, French, and Italian translations are provided in the standard Concrete CMS format under:

```text
languages/de_DE/LC_MESSAGES/messages.po
languages/de_DE/LC_MESSAGES/messages.mo
languages/fr_FR/LC_MESSAGES/messages.po
languages/fr_FR/LC_MESSAGES/messages.mo
languages/it_IT/LC_MESSAGES/messages.po
languages/it_IT/LC_MESSAGES/messages.mo
```

Translated JavaScript strings are supplied server-side through Concrete CMS `t()`. The JavaScript therefore contains no hard-coded German interface text.

## Preview accuracy

All cards are rendered locally. They approximate documented card formats and typical current client implementations, but they are not screenshots generated by the platforms themselves.

- X distinguishes between `summary` cards with a square image and `summary_large_image` cards with an image ratio of approximately 2:1.
- Facebook generally prefers an image ratio of approximately 1.91:1 for large link cards, commonly 1200 × 630 px.
- Telegram generates link previews server-side. The layout and image crop may vary depending on the content and client.
- Nostr is a protocol rather than a single interface. Clients may process Open Graph metadata differently, so the displayed card is explicitly a representative approximation.
- LinkedIn expects `og:title`, `og:image`, `og:description`, and `og:url`. Large cards should use an image of at least 1200 × 627 px with an aspect ratio of approximately 1.91:1.
- Bluesky stores link cards as `app.bsky.embed.external` records containing a URL, title, description, and optional thumbnail. These values are generated by the posting application, so the local card only previews the data that such an application may use.
- Mastodon generates preview cards from Open Graph metadata. Layout, text truncation, and metadata retrieval may vary between instances and clients.

Crawler accessibility, platform caches, and platform-specific moderation cannot be checked locally. After publishing, using the Facebook Sharing Debugger and testing a publicly accessible URL on X is recommended.

## Validation rules

Platform tabs display the overall validation status without showing a problem count:

- Green means that no errors or warnings were found.
- Red means that at least one item requires attention.
- Informational notices alone do not change a tab to red.

Detailed findings are shown in the corresponding **Check** panel.

### Errors

Errors are reported when:

- No usable title, image, or URL is available.
- An unknown X card type is specified.
- A known X image size is below the required minimum.
- Facebook is missing `og:title`, `og:image`, `og:url`, or `og:type`.
- A known Facebook image size is below 200 × 200 px.
- LinkedIn is missing `og:title`, `og:image`, `og:description`, or `og:url`.
- A known LinkedIn image size is below the recommended minimum of 1200 × 627 px.

### Warnings

Warnings are reported when:

- The description or image alternative text is missing.
- The image URL is not an absolute HTTP(S) URL.
- The image ratio differs significantly from the recommended platform format.
- `twitter:card` is missing.
- An X app or player card can only be approximated as a link card.
- Telegram, Bluesky, or Mastodon receives incomplete Open Graph metadata.

### Informational notices

Informational notices explain conditions that do not require an immediate correction, including:

- Differences between Nostr clients
- Differences between Mastodon clients and instances
- The creation of Bluesky external embeds by the posting application

Fallback data from Concrete, standard HTML, or JSON-LD may complete the local preview. When a platform explicitly expects particular metadata, missing fields are still reported even if a local fallback is available. This prevents the preview from implying that the remote platform will necessarily produce the same result.
